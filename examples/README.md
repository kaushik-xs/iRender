# Examples

Each example shows a different way that parts of a page are dynamic. All commands run from the repository root.

## Browse them all

```sh
examples/build.sh             # renders everything into target/site
python3 examples/serve.py     # open http://localhost:8000
```

The script renders every example, plus an index page linking them, into one folder. The index is itself an iRender document: `index.yaml` with `index.data.json` as its data. To list a new example, add it to `index.data.json` and to `build.sh`. Serve the folder instead of opening the files, because the search example fetches its API and browsers block that for `file://` pages. `serve.py` is a static server that also answers the chart gallery's live endpoints. `python3 -m http.server 8000 -d target/site` serves everything else.

The sections below render each example on its own.

| example | dynamic part comes from | features |
|---|---|---|
| [`counter.yaml`](counter.yaml) | browser state | `set_state`, live styles |
| [`product.json`](product.json) | server data + browser state | bindings, `call`, server-rendered `list` |
| [`dashboard/`](dashboard/) | server data assembled per request | `include` from a folder, nested fragments, document `fragments`, `if` on server data, `if` on state inside a table |
| [`search/`](search/) | API calls from the browser | `mount`, `submit` into state, URLs built from state, lists rebuilt from responses, nested reactive lists, loading/empty states |
| [`wizard.yaml`](wizard.yaml) | browser state only | multi-step `if`, conditional fields, validation expressions, two-way bound inputs, `call` to the host |
| [`ui-kit/gallery.yaml`](ui-kit/gallery.yaml) | browser state + an API | every `irender-ui-kit` component, including the react-select-style `ui-combobox`; render with `--ui-kit`, and serve it for load-as-you-type |
| [`blocks/`](blocks/) | server data + browser state | whole pages in the style of shadcn/ui's blocks: a dashboard (inset `ui-sidebar`, summary cards, an area chart filtered by a toggle group, a table with selection and paging, a ⌘K command palette), sidebars that collapse to icons or slide away, login and sign-up pages, account settings, a pricing page and a theme customizer (`theme.options`); render with `--ui-kit --chart-kit --icon-kit` |
| [`charts/gallery.yaml`](charts/gallery.yaml) | server data + browser state + an API | `irender-chart-kit`: every ECharts category, charts driven by ui-kit controls, drill-downs, cross-filtering by click, date range, legend and brush, and live polled and streamed data from `serve.py`; render with `--ui-kit --chart-kit` |
| [`icons/gallery.yaml`](icons/gallery.yaml) | server data (the kit's pack listing) + browser state | `irender-icon-kit`: every pack and icon, sizes and stroke widths, icons in buttons, switching icons with `if` / `else`; render with `--ui-kit --icon-kit` and `--data` from `irender icons --json` |
| [`storefront/`](storefront/) + [`storefront.rs`](../crates/irender-html/examples/storefront.rs) | config generated by Rust code from services | a custom `Fragments` source, A/B layouts, feature flags, host JS driving a cart through `call` and `set` |

## Dashboard

An orders dashboard. A host would fill `dashboard.data.json` from its APIs on each request.

```sh
cargo run -p irender-cli -- render examples/dashboard/dashboard.yaml \
  --data examples/dashboard/dashboard.data.json --fragments examples/dashboard/fragments -o dashboard.html
```

- `stat-card`, `order-row` and `status-badge` come from `fragments/`. `order-row` includes `status-badge`, and both read the `order` the surrounding list defines.
- `order-lines` is defined inside the document's own `fragments`.
- The admin buttons and the alert banner are `if`s on server data. A viewer with `"role": "viewer"` or no alerts gets no trace of them in the HTML.
- The filter tabs and expandable rows are `if`s on state. Every row is rendered on the server, and the browser only shows and hides them, even inside `<tbody>`.

## Search

A product search that loads its results from an API. Fetching needs HTTP, so render the page next to the mock API and serve the folder:

```sh
cargo run -p irender-cli -- render examples/search/search.json -o examples/search/index.html
python3 -m http.server 8000 -d examples/search      # open http://localhost:8000
```

- `on.mount` on the root fetches `api/{{ category }}.json` when the page opens. The tabs and the search form fetch again, and a `loading` flag around each `submit` drives the status line and the button.
- The result cards are a `list` over `{{ results.items }}`. Each response rebuilds them, and the tags inside each card are a nested list over the card's own `p.tags`.
- `garden` returns no items and shows the empty state. Low stock and sold-out notes are `if`s on each item.
- *Details* stores the item in `selected`, which opens the side panel. Each card reports an `impression` through a `mount` action.
- The mock API is static files, so it ignores `?q=`. A real endpoint would filter by it.

## Wizard

```sh
cargo run -p irender-cli -- render examples/wizard.yaml -o wizard.html
```

Four steps, each an `if` on `step`. Choosing *Team* reveals a seats field and *Enterprise* a company field. *Next* stays disabled until the current step is valid. Going back keeps every input, because hidden steps keep their DOM. *Create account* sends all the answers to the host with `call` and shows a confirmation.

## Storefront

The layout in `storefront/storefront.json` is fixed, but three of its parts are generated by Rust code at load time from simulated service calls:

```sh
cargo run -p irender-html --example storefront > storefront.html
cargo run -p irender-html --example storefront -- --variant b > storefront-b.html   # other A/B layout
cargo run -p irender-html --example storefront -- --no-campaign --no-recs > plain.html
```

- `nav` is one link per category from the catalog.
- `hero` is a different node structure per A/B variant, or nothing when no campaign runs.
- `recommendations` exists only when the flag is on, with the API response baked in.
- The user and products are per-request `data`.
- The cart lives in the browser. *Add* and *✕* are `call` actions, and a small host script owns the cart logic and writes `cart`, `count` and `total` back with `root.__irender.set`, which rebuilds the cart list.
